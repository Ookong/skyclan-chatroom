## 一、为什么会出现事故

**直接原因：** `docs/index.html` 内嵌 JS 的 `lessonCacheAdd` 缺一个右括号 `}`——语法错误使整个 script 块解析失败，后续所有函数（含 app 初始化）一行都没执行。

三个叠加因素让它发生且**无声**：

1. **无门禁** —— 当时 site/ 代码改动不走 mentor 审查（双签只覆盖规则文档），代码直上生产
2. **无检查** —— 内嵌 JS 的 HTML 没有任何语法检查环节，错一个括号照样 commit + 上线
3. **无声死亡** —— spinner 是 CSS 实现的，JS 死了照样转圈。症状看起来像「网络慢」而不是「程序死了」，迷惑性极强

---

## 二、为什么长期得不到解决（误诊链，最难看但最重要）

| 层级 | 时间 | 诊断 | 结果 |
|------|------|------|------|
| 第 1 层 | 8/31 23:35 | 网络抖动（workers.dev 间歇不可达是 8/27 已知真问题 + 前端串行 fetch 无重试） | 有真实成分，但漏了真凶 |
| 第 2 层 | 9/1 17:42 | SW 缓存污染 → cache v2 强刷 | 治缓存层，与语法错误无关 |
| 第 3 层 | 9/2 凌晨 | 前端韧性不足 → 三件套（本地缓存 + 双域名竞速 + 后台刷新） | 在错误假设下越做越精，方向就是错的 |
| 转机 | 9/2 09:29 | Tree 追问 deadline，被迫从零验证 → `node --check` 十分钟抓到 | 真凶落网 |

**根因：排查从「最像的假设」开始，而不是从「最小验证」开始。**

浏览器控制台那个红色 `SyntaxError` 摆了 37 个小时，打开看一眼只要 10 秒；而我们所有验证都打在 API 层（curl 8/8 全 200——API 本来就没病）。首诊网络结论是如意下的，这层责任如意认。
